# Домашнее задание к занятию «Микросервисы: подходы»

Компания строит систему на основе микросервисной архитектуры. Ниже представлены
предложения по организации инфраструктуры для разработки и эксплуатации: система
непрерывной интеграции/поставки, централизованный сбор логов и мониторинг.

## Задача 1: Обеспечить разработку

### Требования

- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

### Предлагаемое решение: GitLab (SaaS) + self-hosted GitLab Runners

GitLab закрывает и хранение кода, и CI/CD в рамках одного продукта, что упрощает
эксплуатацию — не нужно интегрировать отдельно систему контроля версий и отдельно
CI-сервер.

**Архитектура:**
- **GitLab.com (облачный SaaS)** — центральный git-хостинг и оркестратор CI/CD-пайплайнов.
- Каждый микросервис — отдельный **проект/репозиторий** в GitLab, сгруппированный по доменам через Groups/Subgroups.
- **GitLab Runners** разворачиваются на собственных серверах компании (self-hosted) и регистрируются в облачном GitLab — таким образом сборки физически выполняются на своих мощностях, а управление пайплайнами остаётся в облаке.
- **GitLab Container Registry** используется для хранения собственных Docker-образов сборщиков.

**Соответствие требованиям:**

| Требование | Как реализуется |
|---|---|
| Облачная система | GitLab.com — полностью SaaS |
| Git VCS | GitLab нативно построен на Git |
| Репозиторий на каждый сервис | Отдельный проект в GitLab на микросервис |
| Запуск по событию VCS | Pipeline триггерится автоматически на push/merge request/tag через правила `rules`/`only` в `.gitlab-ci.yml` |
| Запуск по кнопке с параметрами | Кнопка «Run pipeline» в UI с вводом CI/CD-переменных вручную; джобы с `when: manual` |
| Настройки, привязанные к сборке | CI/CD Variables на уровне job/branch/environment, protected-переменные для защищённых веток |
| Шаблоны конфигураций сборок | Директива `include:` — общий репозиторий с переиспользуемыми шаблонами пайплайнов, наследование через `extends` |
| Безопасное хранение секретов | Masked & Protected CI/CD Variables; интеграция с HashiCorp Vault через ключевое слово `vault` |
| Несколько конфигураций из одного репозитория | Родительско-дочерние (parent-child) пайплайны, множественные `rules`, несколько `include`-файлов под разные окружения (dev/staging/prod) |
| Кастомные шаги сборки | Произвольные shell/script-команды в джобах на любом этапе (`stage`) |
| Собственные Docker-образы для сборки | Ключевое слово `image:` в джобе, свои образы хранятся в GitLab Container Registry |
| Агенты сборки на своих серверах | Self-hosted GitLab Runner, регистрируемый в облачном GitLab (гибридная схема) |
| Параллельный запуск сборок | Несколько runner'ов + параллельные джобы в рамках одного этапа |
| Параллельный запуск тестов | Директива `parallel:` — разбиение тестового набора на N параллельных джобов |

**Обоснование выбора:** GitLab закрывает весь список требований одним продуктом,
без необходимости связывать между собой отдельный git-хостинг (GitHub/Bitbucket) и
отдельный CI-сервер (TeamCity/Jenkins), как это потребовалось бы, например, в связке
GitHub + TeamCity. Гибридная модель (SaaS-оркестрация + self-hosted runners)
позволяет держать конфиденциальные исходники и секреты компании под контролем на
собственных агентах, не теряя удобства облачного управления. При этом гибкость
`.gitlab-ci.yml` (шаблоны, parent-child pipelines, matrix-параллелизм) полностью
покрывает требования по кастомизации и множественным конфигурациям сборки.

## Задача 2: Логи

### Требования

- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

### Предлагаемое решение: EFK/ELK-стек (Filebeat → Logstash → Elasticsearch → Kibana)

**Архитектура:**
- **Filebeat** разворачивается на каждом хосте (или как DaemonSet в Kubernetes) и читает логи контейнеров напрямую из stdout/stderr (через файлы, в которые Docker/containerd пишет json-логи) — приложениям не нужно ничего менять в коде логирования.
- Filebeat отправляет логи в **Logstash**, где происходит парсинг, обогащение метаданными (сервис, хост, окружение) и нормализация формата.
- Logstash пишет обработанные записи в кластер **Elasticsearch**, который выступает центральным хранилищем и поисковым индексом.
- **Kibana** предоставляет веб-интерфейс поверх Elasticsearch: полнотекстовый поиск, фильтрация по полям, построение дашбордов.

**Соответствие требованиям:**

| Требование | Как реализуется |
|---|---|
| Сбор логов со всех хостов в центральное хранилище | Filebeat на каждом хосте → единый кластер Elasticsearch |
| Минимальные требования к приложениям, сбор из stdout | Приложение просто пишет в stdout — Filebeat читает файлы логов драйвера Docker/K8s, доп. интеграция не нужна |
| Гарантированная доставка | Filebeat использует локальный registry-файл и ack-протокол (at-least-once delivery) с повторными попытками при недоступности Logstash/Elasticsearch; при высокой нагрузке между Filebeat и Logstash можно добавить Kafka как буфер для устойчивости к простоям хранилища |
| Поиск и фильтрация по логам | Elasticsearch — полнотекстовый и структурированный поиск (Query DSL, KQL) |
| UI с доступом для разработчиков | Kibana с ролевым разграничением доступа (Elastic Security/RBAC) — можно выдавать read-only доступ к нужным индексам конкретным командам |
| Ссылка на сохранённый поиск | Kibana Saved Search + функция «Share» генерирует постоянную ссылку на сохранённый запрос/дашборд |

**Обоснование выбора:** ELK/EFK — зрелый и широко распространённый стек именно для
задач централизованного логирования в микросервисной архитектуре. Использование
Filebeat как лёгкого агента снимает требования к приложениям (не нужен ни SDK, ни
изменение формата логирования — достаточно писать в stdout, что уже является
стандартной практикой в контейнеризированных системах). Разделение сбора (Filebeat),
обработки (Logstash) и хранения/поиска (Elasticsearch) позволяет масштабировать
каждый компонент независимо, а Kibana закрывает оба требования к
пользовательскому интерфейсу — поиск с разграничением доступа и шаринг сохранённых
запросов.

## Задача 3: Мониторинг

### Требования

- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

### Предлагаемое решение: Prometheus + Node Exporter + cAdvisor + Grafana

**Архитектура:**
- **Node Exporter** устанавливается на каждый хост и отдаёт метрики уровня ОС (CPU, RAM, диск, сеть).
- **cAdvisor** (или `kube-state-metrics`/встроенные метрики оркестратора, если используется Kubernetes) собирает метрики потребления ресурсов по каждому контейнеру/сервису отдельно.
- Каждый микросервис инструментируется клиентской библиотекой Prometheus и отдаёт специфичные бизнес- и технические метрики на своём `/metrics`-эндпоинте.
- **Prometheus Server** централизованно опрашивает (scrape) все эти источники по конфигурации service discovery (K8s/Consul/статический список) и хранит временные ряды.
- **Grafana** подключается к Prometheus как источнику данных и предоставляет UI для запросов (PromQL) и построения дашбордов.

**Соответствие требованиям:**

| Требование | Как реализуется |
|---|---|
| Сбор метрик со всех хостов | Node Exporter на каждом хосте, опрашивается Prometheus |
| Метрики ресурсов хостов (CPU/RAM/HDD/Network) | Экспортируются Node Exporter |
| Метрики потребляемых ресурсов сервиса | cAdvisor / kube-state-metrics — метрики по каждому контейнеру отдельно |
| Метрики, специфичные для сервиса | Собственный `/metrics`-эндпоинт сервиса через клиентскую библиотеку Prometheus |
| UI для запросов и агрегации | Grafana Explore / встроенный expression browser Prometheus с языком запросов PromQL |
| UI с настраиваемыми панелями | Grafana Dashboards — гибкая настройка панелей под хосты и сервисы |

**Обоснование выбора:** связка Prometheus + Grafana — фактический стандарт
мониторинга в микросервисных и контейнеризированных системах. Pull-модель
Prometheus упрощает добавление новых хостов и сервисов (достаточно зарегистрировать
target в service discovery), а разделение экспортёров (Node Exporter — хосты,
cAdvisor — контейнеры, кастомные `/metrics` — бизнес-логика) даёт нужную детализацию
метрик без единой точки отказа. Grafana поверх Prometheus закрывает оба требования к
интерфейсу: произвольные агрегирующие запросы и настраиваемые дашборды для разных
команд и уровней системы (инфраструктура/сервис/бизнес-метрики).
