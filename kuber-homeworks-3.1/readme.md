# Домашнее задание: расчёт требований к кластеру Kubernetes

## Цель
Рассчитать, сколько worker-нод и какого размера нужно под проект: БД + кеш (обе отказоустойчивые) + бекенд + фронтенд.

---

## Шаг 1. Упаковка в Helm-чарт (требование 1)

Прежде чем считать цифры — они должны быть параметрами чарта, а не хардкодом, чтобы один чарт разворачивался в dev/stage/prod с разными значениями:

- `values.yaml` (base) + `values-dev.yaml` / `values-staging.yaml` / `values-prod.yaml` с переопределением `replicaCount` и `resources` для каждого компонента.
- Для каждого компонента задаём `resources.requests` = реальному потреблению (см. таблицу ниже), `resources.limits` — с запасом ×1.3–1.5, чтобы допускать всплески, но не давать одному поду «съесть» всю ноду.
- Для БД и кеша — `StatefulSet` + `podAntiAffinity` (по возможности `requiredDuringSchedulingIgnoredDuringExecution`), чтобы реплики гарантированно расходились по разным нодам, и `PodDisruptionBudget` (`minAvailable: 2` из 3), чтобы при обновлении/дрейне ноды не терять кворум.
- Фронтенд/бекенд — обычный `Deployment` + `HorizontalPodAutoscaler`, т.к. это stateless-нагрузка.
- `nodeSelector`/taints-tolerations, чтобы развести стейтфул- и стейтлесс-нагрузку по разным пулам нод (обоснование — ниже).

| Компонент | RAM/под | CPU/под | Реплик | RAM итого | CPU итого |

## Шаг 3. Прикидка количества worker-нод (требования 3–5)

БД и кеш — «тяжёлые по памяти» (1 CPU на 4 ГБ RAM, соотношение 1:4), бекенд — «тяжёлый по CPU» (1 CPU на 0.6 ГБ, соотношение ~1:0.6), фронтенд — лёгкий. Разная профильность нагрузки — повод развести их по **двум пулам нод разного размера** (как и просит пункт 5 задания: «для разных типов нод требования разные»).

### Пул 1 — stateful (БД + кеш)

Размер ноды: **4 vCPU / 16 ГБ RAM**.

Служебный резерв на ноду (kubelet, container runtime, kube-proxy, CNI-демонсет, агенты мониторинга/логирования) — обычно 15–25% ресурсов ноды, возьмём ~1 vCPU / 2 ГБ:
→ allocatable ≈ **3 vCPU / 14 ГБ** на ноду.

На одну ноду помещается 1 реплика БД + 1 реплика кеша = 2 vCPU / 8 ГБ — укладывается с запасом в allocatable.

Минимум для равномерного распределения (по одной реплике БД и кеша на ноду, требование anti-affinity для отказоустойчивости) — **3 ноды**.

Запас на отказ одной ноды (требование 4): если нода упадёт, поды с неё должны переехать на оставшиеся — а значит, свободная ёмкость под них должна быть заранее заложена, иначе кворум БД/кеша просядет и останется без возможности пересборки:
→ **3 + 1 = 4 ноды** в пуле.

Проверка ёмкости на 4 нодах: allocatable 12 vCPU / 56 ГБ против потребности 6 vCPU / 24 ГБ — запас есть, включая место для пересъезда пода с упавшей ноды.

### Пул 2 — stateless (фронтенд + бекенд)

Размер ноды: **4 vCPU / 8 ГБ RAM** (соотношение CPU:RAM ближе к профилю бекенда, который упирается в CPU, а не в память).

Служебный резерв — меньше, чем для stateful-пула (эти ноды проще, без тяжёлых I/O-нагрузок), возьмём ~0.5–1 vCPU / 1 ГБ:
→ allocatable ≈ **3 vCPU / 7 ГБ** на ноду.

Бекенд (1 vCPU / 0.6 ГБ на под) упирается в CPU: 3 vCPU allocatable / 1 vCPU на под = 3 бекенд-пода на ноду (память при этом используется всего на 1.8 из 7 ГБ — не лимитирующий фактор).

Суммарная потребность пула: 11 vCPU (1 от фронтенда + 10 от бекенда), 6.25 ГБ RAM.

Нод по CPU: 11 / 3 ≈ 3.7 → округляем вверх — **4 ноды**.
По RAM: 6.25 / 7 ≈ 0.9 → RAM явно не лимитирует.

Запас на отказ одной ноды: **4 + 1 = 5 нод** в пуле.

## Шаг 4. Итог: количество нод и их параметры (требование 6)

| Пул | Кол-во нод | vCPU/нода | RAM/нода | Allocatable (после резерва) | Назначение |
|---|---|---|---|---|---|
| Stateful | **4** | 4 | 16 ГБ | ~3 vCPU / 14 ГБ | БД (3 реплики) + Кеш (3 реплики), по одной паре на ноду + 1 нода про запас |
| Stateless | **5** | 4 | 8 ГБ | ~3 vCPU / 7 ГБ | Фронтенд (5 реплик) + Бекенд (10 реплик), 1 нода про запас |
| **Всего worker-нод** | **9** | — | — | ~27 vCPU / ~88 ГБ allocatable | vs потребность 17 vCPU / 30.25 ГБ (запас ~1.6–2×) |

Запас 1.6–2× — это не «жир», а сумма:
- места под пересъезд подов при падении одной ноды в каждом пуле,
- служебных ресурсов на каждой ноде (kubelet, CNI, kube-proxy, агенты),
- задела под рост числа реплик (HPA для бекенда/фронтенда) без немедленного добавления нод.

### Control-plane

Отдельно от worker-нод:
- Если кластер self-managed (kubeadm/RKE и т.п.) — 3 ноды control-plane для отказоустойчивого кворума etcd, размер можно взять скромный, например 2 vCPU / 4–8 ГБ каждая (нагрузка на control-plane для кластера такого масштаба невелика, но кворум etcd всё равно требует минимум 3 узла).
- Если используется managed Kubernetes (EKS/GKE/AKS/Yandex Managed Service for K8s) — control-plane предоставляется облаком, отдельные ноды считать не нужно.

### Итоговая конфигурация кластера

- **Control-plane:** 3 ноды × 2 vCPU / 4–8 ГБ (или managed control-plane)
- **Worker, stateful pool:** 4 ноды × 4 vCPU / 16 ГБ
- **Worker, stateless pool:** 5 нод × 4 vCPU / 8 ГБ
- **Итого worker-нод: 9**, суммарно ~36 vCPU / 104 ГБ «сырой» ёмкости (allocatable ~27 vCPU / 88 ГБ) под нагрузку в 17 vCPU / 30.25 ГБ.
