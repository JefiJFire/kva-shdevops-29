# Домашнее задание к занятию «Микросервисы: принципы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.

## Задача 1: API Gateway 

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:
- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.

### Сравнительная таблица

| Критерий | Kong Gateway | NGINX (+Ingress) | Traefik | Amazon API Gateway |
|---|---|---|---|---|
| Маршрутизация по конфигурации | Да (декларативная/DB-driven) | Да (конфиг-файлы, шаблоны) | Да (авто-обнаружение через Docker/K8s labels) | Да (managed, через консоль/IaC) |
| Проверка аутентификации (JWT, OAuth2, key-auth, Basic) | Встроенные плагины «из коробки» | Через модули/Lua-скрипты (сложнее) | Есть middleware, набор скромнее | Встроено (Cognito, IAM, Lambda authorizer) |
| Терминация HTTPS | Да | Да | Да, включая авто Let's Encrypt | Да (managed) |
| Кластеризация/масштабирование | Да, горизонтально | Да (за отдельным LB) | Да | Managed, авто |
| Расширяемость (плагины) | Богатая экосистема (rate-limit, ACL, логирование) | Требует ручной разработки модулей | Меньше плагинов, проще интеграция с K8s | Ограничено экосистемой AWS |
| Простота эксплуатации в K8s/микросервисах | Хорошая (Ingress Controller) | Средняя, много ручной настройки | Отличная (нативная интеграция с Docker/K8s) | Отличная, но vendor lock-in |
| Стоимость / open-source | Open-source + Enterprise | Open-source (бесплатно) | Open-source (бесплатно) | Платно по трафику |
| Наблюдаемость (метрики, трейсинг) | Встроено (Prometheus plugin) | Через доп. модули | Встроенный dashboard + Prometheus | Встроено (CloudWatch) |

### Выбор: Kong Gateway

Обоснование выбора:

- Все три требования закрываются «из коробки»: маршрутизация через декларативные конфиги (YAML/DB), плагины `jwt`, `oauth2`, `key-auth`, `acl` для проверки аутентификации, плагин/встроенный SSL-termination для HTTPS.
- Не привязывает компанию к одному облачному провайдеру (в отличие от AWS API Gateway) — важно при гибридной или мультиоблачной инфраструктуре.
- Богатая экосистема плагинов позволяет добавлять rate limiting, логирование, трансформацию запросов без написания кода — снижает нагрузку на DevOps.
- Есть Kubernetes Ingress Controller — удобно вписывается в микросервисную инфраструктуру на K8s.
- По сравнению с чистым NGINX не требует написания Lua-скриптов для аутентификации — быстрее внедрение и ниже порог входа для команды.

## Задача 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:
- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Обоснуйте свой выбор.

### Сравнительная таблица

| Критерий | Apache Kafka | RabbitMQ | Redis Streams | ActiveMQ Artemis |
|---|---|---|---|---|
| Кластеризация | Да (Kafka Cluster + ZooKeeper/KRaft), надёжная репликация партиций | Да (mirrored/quorum queues) | Да (Redis Cluster), менее зрелая для очередей | Да, но сложнее в настройке |
| Персистентность на диске | Да, лог-структурированное хранение по умолчанию | Да (durable queues) | Опционально (AOF/RDB) | Да |
| Скорость / пропускная способность | Очень высокая (млн msg/sec) | Высокая, ниже Kafka на больших объёмах | Очень высокая (in-memory) | Средняя-высокая |
| Форматы сообщений | Любые (byte payload + Schema Registry: Avro/JSON/Protobuf) | Любые (byte payload), гибко | Любые (byte payload) | Любые + JMS-форматы |
| Разграничение прав доступа (ACL) | Да, детальные ACL по топикам | Да, права по vhost/очередям/exchange | Ограниченно (ACL в поздних версиях) | Да (JAAS) |
| Простота эксплуатации | Средняя-сложная (партиции, ребалансировка) | Простая (удобный UI, понятная модель) | Простая, но не для сложных сценариев доставки | Сложнее, менее популярна |
| Модель доставки | Publish-Subscribe, log-based, replay сообщений | Очереди + Pub/Sub (exchange/routing) | Consumer groups, streams | Очереди + Pub/Sub (JMS) |
| Экосистема/поддержка | Огромная, стандарт де-факто для микросервисов | Широкая, зрелая | Растущая | Ограниченная |

### Выбор: Apache Kafka

Обоснование выбора:

- **Кластеризация**: Kafka изначально проектировался как распределённая система — партиции реплицируются между брокерами, что обеспечивает высокую надёжность.
- **Персистентность**: сообщения по умолчанию пишутся на диск в виде упорядоченного лога и хранятся заданное время/объём — это даёт возможность replay и устойчивость к сбоям consumer'ов.
- **Скорость**: за счёт последовательной записи на диск и батчинга Kafka обеспечивает очень высокую пропускную способность, что критично при большом числе микросервисов.
- **Форматы сообщений**: сам брокер работает с байтовым payload, а Schema Registry позволяет стандартизировать форматы (Avro, JSON, Protobuf) между командами.
- **Права доступа**: ACL позволяют точечно разграничивать доступ на чтение/запись по топикам — удобно для крупной компании с множеством команд.
- **Простота эксплуатации**: ниже, чем у RabbitMQ (нужен опыт с партициями, ребалансировкой, KRaft/ZooKeeper). Но при масштабе «крупная компания с микросервисной архитектурой» долгосрочные выгоды (пропускная способность, replay, экосистема Kafka Connect/Streams) перевешивают сложность внедрения. Если бы приоритетом была именно простота эксплуатации при умеренной нагрузке — разумной альтернативой было бы RabbitMQ.
